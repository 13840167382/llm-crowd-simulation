后端技术细节总结

本文档用于快速理解后端项目的主要技术实现、运行链路和排障关注点。内容基于当前 `backend/app` 代码结构整理，重点覆盖请求入口、实验生命周期、决策引擎、轨迹写入、分析聚合、维护任务、RQ worker、Redis 缓存和数据库访问。

## 1. 项目分层

后端整体按以下层次组织：

| 层级 | 目录 | 主要职责 |
| --- | --- | --- |
| API 层 | `app/api` | FastAPI 路由、请求头校验、统一响应、异常处理、幂等包装 |
| Application 层 | `app/application` | 业务用例编排，例如实验、拓扑、人群分配、决策、轨迹、分析、维护 |
| Domain 层 | `app/domain` | 枚举和值对象等领域概念 |
| Infrastructure 层 | `app/infrastructure` | 数据库模型/仓储、Redis、RQ worker、日志、LLM provider |
| Schema 层 | `app/schemas` | Pydantic 请求/响应模型 |
| Core 层 | `app/core` | 配置、上下文、精度处理、常量、环境加载 |

业务逻辑主要在 `app/application/*/service.py`，仓储层只负责数据库读写，不承担复杂业务判断。

## 2. 应用启动与请求上下文

应用入口是 `app/main.py`：

- `create_app()` 创建 FastAPI 实例，注册异常处理、请求中间件、健康检查和 API 路由。
- `lifespan()` 在启动时配置日志，在关闭时释放 Redis 连接。
- 请求中间件会读取或生成 `X-Request-Id`，同时读取 `X-Experiment-Id`，写入 `contextvars`。
- 日志过滤器会从 `contextvars` 读取 `request_id` 和 `experiment_id`，让业务日志自动带上下文。
- 每个响应都会回写 `X-Request-Id`，方便前后端联合排查。

配置入口是 `app/core/config.py`：

- 模块导入时会先加载 `.env` 文件。
- `get_settings()` 把环境变量转换为强类型 `Settings`，并使用 `lru_cache` 缓存。
- 如果测试或脚本需要切换环境变量，需要清理 `get_settings` 缓存或重启进程。

数据库入口是 `app/infrastructure/db/session.py`：

- `get_engine()` 创建并缓存 SQLAlchemy Engine。
- `pool_pre_ping=True` 用于降低长时间运行后 stale connection 的概率。
- `get_db_session()` 只负责请求结束后关闭 Session，不自动提交。
- 业务层自行决定 `flush()`、`commit()` 和 `rollback()` 时机。

## 3. API 幂等机制

通用幂等组件在 `app/api/idempotency.py`，主要用于写请求：

- 只有客户端传入 `X-Request-Id` 且 Redis 启用时才生效。
- 请求体、路径参数等关键数据会被序列化成 `request_hash`。
- Redis 保存两类 key：
  - 响应快照：相同请求命中后直接回放之前的 JSONResponse。
  - 短 TTL 锁：防止同一个 `X-Request-Id` 的请求并发进入业务层。
- 如果同一个 `X-Request-Id` 被用于不同请求体，会返回冲突错误。

目前决策批次和轨迹批次路由都使用了该机制：

- `POST /api/v1/experiments/{experiment_id}/decisions`
- `POST /api/v1/experiments/{experiment_id}/trajectories`

同时这些路由会校验 `X-Experiment-Id` 必须和路径里的 `experiment_id` 一致。

## 4. 实验生命周期

实验生命周期由 `app/application/experiments/service.py` 编排：

1. 创建实验后状态为 `initialized`。
2. 拓扑和人群分配补齐后，预运行状态可刷新为 `ready`。
3. `start_experiment()` 只允许在准备完成后启动，状态进入 `running`。
4. `complete_experiment()` 完成实验，并入队维护任务。
5. `fail_experiment()` 标记失败，并生成失败摘要。

实验完成时默认入队的维护链路是：

```text
analytics_refresh -> heatmap_prewarm -> runtime_data_cleanup -> experiment_archive
```

其中 `experiment_archive` 不是完成实验时直接入队，而是在运行数据清理成功后再入队，这样归档摘要能记录清理结果。

## 5. 拓扑、人群分配与出生点

拓扑服务在 `app/application/topology/service.py`：

- 拓扑采用全量替换策略。
- 更新拓扑会删除旧 zone 和 exit，再写入新拓扑。
- 拓扑变化会影响人群分配和出生点，因此更新前会校验实验仍可编辑。

人群分配和出生点服务在 `app/application/allocation_spawn/service.py`：

- 分配写入后会生成每类人群的数量、颜色、参数快照。
- 出生点生成支持固定区域、权重区域、入口随机、点位扩散等模式。
- 同一个 seed 可以复现出生点。
- 如果 seed 或分配发生变化，会删除旧 agents 并重新生成，避免前端看到混合数据。

## 6. 决策批次链路

决策入口是 `app/application/decisions/service.py`。

一次决策批次的主要流程：

1. 校验实验必须是 `running`。
2. 数据库查询同一实验、同一 `batch_id` 是否已存在，命中则直接返回历史响应。
3. 获取 Redis 批次锁，防止同一个 `batch_id` 并发重复处理。
4. 获取 Redis 实验锁，限制同一实验同一时间只有一个决策批次在执行。
5. 插入 `PROCESSING` 状态的 `decision_batches` 记录。
6. 根据配置选择本地启发式引擎或真实模型引擎。
7. 串行或有限并发处理每个 agent。
8. 写入 `agent_decisions` 明细。
9. 更新 `decision_batches` 响应快照和状态。
10. 刷新决策、人物相关分钟聚合。
11. 释放 Redis 锁。

### 并发与超时

批次处理支持有限并发：

- 并发上限由 `APP_DECISION_BATCH_MAX_CONCURRENCY` 控制。
- 批次硬超时由 `APP_DECISION_BATCH_HARD_TIMEOUT_SECONDS` 控制。
- 并发结果会按输入 agent 的原始顺序回填，保证响应顺序和请求顺序一致。
- 批次超时后，未完成的 agent 会统一生成 timeout fallback/none 结果。

### LLM 与 fallback

决策引擎公共接口在 `app/application/decisions/engine.py`：

- `heuristic/mock/local` 使用本地启发式引擎。
- `openai/openai_compatible/llm` 使用 OpenAI-compatible 真实模型引擎。

真实模型实现位于 `app/application/decisions/llm_engine.py`：

- 调用 `{base_url}/chat/completions`。
- 请求格式兼容 OpenAI Chat Completions。
- `provider_model` 为空时使用实验里的 `llm_model`。
- 解析失败、HTTP 错误、连接失败都会转换为决策引擎异常。

Prompt 构造在 `prompt_builder.py`，响应解析在 `response_parser.py`：

- Prompt 明确要求模型只能从候选出口中选择。
- 服务端仍会严格校验 `chosen_exit_id` 是否存在于候选出口。
- `confidence` 必须在 `0.0` 到 `1.0` 之间。
- 解析失败是否 fallback，由 service 层根据实验配置决定。

fallback 规则：

- 如果允许 fallback，优先使用 `algorithm_recommendation`。
- 如果算法推荐不存在或不在候选出口里，使用 `algorithm_score` 最高的候选出口。
- 如果不允许 fallback，则返回 `decision_source=none`，由 Unity 侧继续处理。

## 7. 轨迹写入与刷新

轨迹入口是 `app/application/trajectories/service.py`。

一次轨迹上报的主要流程：

1. 校验实验存在且状态允许写入。
2. 根据 `batch_id` 做数据库幂等。
3. 写入 `trajectory_batches`。
4. 批量写入 `trajectory_points`。
5. 提交事务。
6. 尝试投递 RQ 轨迹刷新任务。

轨迹上报的设计原则是：

- 原始轨迹落库是主路径。
- 聚合和采样刷新是异步增强路径。
- 如果 RQ 投递失败，轨迹上报仍然成功，后续可通过维护任务或命令补刷新。

轨迹刷新会更新：

- 区域分钟聚合 `zone_metrics_1m`
- 出口分钟聚合 `exit_metrics_1m`
- 人物分钟聚合 `agent_metrics_1m`
- 秒级采样轨迹 `trajectory_points_sampled_1s`

## 8. 分析聚合与查询

聚合刷新逻辑在 `app/application/analytics/aggregation.py`。

刷新策略：

- 根据受影响的 `simulation_time_ms` 计算分钟桶。
- 对目标分钟桶执行 delete + rebuild。
- 这样重复上报、任务重放、维护补偿时不会累加出错。

主要聚合表：

| 表 | 用途 |
| --- | --- |
| `zone_metrics_1m` | 区域人数、排队、进出、停留、利用率 |
| `exit_metrics_1m` | 出口通行量、排队长度、等待时间 |
| `decision_metrics_1m` | LLM 成功数、fallback 数、override 数、延迟 |
| `agent_metrics_1m` | 总人数、活跃人数、离场人数、速度、停留 |
| `trajectory_points_sampled_1s` | 历史轨迹 compact 查询和回放 |

分析查询入口是 `app/application/analytics/service.py`：

- `running` 实验优先读原始轨迹和决策明细，保证实时性。
- 非运行实验优先读聚合表和采样表，降低查询成本。
- 如果聚合表缺失，会回退原始表。
- 原始运行数据被清理后，精细的单 agent 原始轨迹详情无法完整恢复。

### 热力图缓存

热力图采用三层策略：

```text
Redis 热缓存 -> heatmap_cache 数据库缓存 -> trajectory_points 回源计算
```

如果运行数据已经清理，且没有命中热力图缓存，则不能回源计算，会返回冲突错误。

维护任务会在清理原始轨迹前执行热力图预热，为全体人群和各 crowd_type 生成默认热力图缓存。

## 9. 后台维护任务

维护任务服务在 `app/application/maintenance/service.py`。

维护任务由数据库表 `experiment_maintenance_jobs` 记录，核心状态包括：

- `pending`
- `running`
- `succeeded`
- `failed`

任务类型包括：

- `analytics_refresh`
- `heatmap_prewarm`
- `runtime_data_cleanup`
- `experiment_archive`

任务执行特点：

- 每个任务都要求幂等。
- 任务失败后按配置退避重试。
- 超过最大重试次数后标记为 `failed`。
- 可以通过命令重置失败任务。
- 可以从某个 job 开始重放后续维护链路。

`list_pending_jobs()` 使用数据库行锁：

- `FOR UPDATE SKIP LOCKED` 防止多个 worker 拿到同一条任务。
- 同一实验内，后序任务会等待前序 `pending/running/failed` 任务处理完，保证链路顺序。

## 10. RQ Worker 与本地 Worker

RQ 相关代码在 `app/infrastructure/workers/rq_worker.py`。

RQ 的职责是唤醒 worker，不是维护任务事实来源：

- 数据库里的 `experiment_maintenance_jobs` 是事实来源。
- RQ job 通常只是执行一轮 dispatch 或 trajectory refresh。
- 如果 RQ job 丢失，只要数据库任务还在 pending，就可以重新派发。

RQ 队列共用 Redis 连接：

- maintenance dispatch job
- trajectory refresh job

Windows 兼容：

- RQ 某些模块会调用 `multiprocessing.get_context("fork")`。
- Windows 没有 fork。
- 项目在导入 RQ 前打补丁，把 `fork` context 替换为 `spawn`。
- 如果 scheduler 仍触发平台问题，可以用 `--without-scheduler` 启动 worker。

本地直接执行型 worker 在 `app/infrastructure/workers/tasks.py`：

- 不依赖 RQ。
- 直接轮询数据库 pending 维护任务。
- 适合本地开发、没有 Redis 的环境，或临时补跑。

## 11. Redis 使用方式

Redis 封装在 `app/infrastructure/cache/redis_client.py`。

项目中 Redis 有三类用途：

1. JSON 缓存，例如热力图、幂等响应。
2. 轻量锁，例如 request idempotency、decision batch lock、experiment decision lock。
3. RQ 队列连接。

普通缓存连接使用 `decode_responses=True`，方便读写 JSON 字符串。

RQ 连接使用 `decode_responses=False`，因为 RQ 自己会序列化 job payload，需要二进制连接。

锁释放使用 compare-and-delete：

- 加锁时写入随机 token。
- 释放时只有当前值等于 token 才删除。
- 避免锁 TTL 到期后被其他请求重新获得，又被旧请求误删。

## 12. TimescaleDB 与原始轨迹

轨迹点表依赖 TimescaleDB hypertable 能力。

数据库健康检查除了 `SELECT 1`，还会检查 TimescaleDB 扩展状态，因为：

- 数据库可连接不代表轨迹链路完整可用。
- 原始轨迹写入、时间范围查询、聚合刷新都依赖时间序列能力。

原始运行数据清理策略：

- 清理前刷新聚合和采样。
- 可选择是否清理热力图缓存。
- 保留实验主记录、拓扑、分配、出生点、聚合表、采样表、维护任务、归档记录。
- 删除 `decision_batches`、`agent_decisions`、`trajectory_batches`、`trajectory_points` 等原始运行明细。

## 13. 常见排障路径

### 决策批次重复或卡住

优先检查：

- `decision_batches` 是否已有同一 `experiment_id + batch_id`。
- Redis 中是否存在 decision batch lock。
- Redis 中是否存在 experiment decision lock。
- 实验是否仍是 `running`。
- LLM 服务是否可用。
- 是否触发批次硬超时。

### RQ worker 启动报 fork 错误

这是 Windows 平台和 RQ scheduler/fork 相关的问题。

处理方向：

- 使用项目里的 RQ Windows 兼容补丁入口启动。
- Windows 本地可使用 `--without-scheduler`。
- 或改用本地直接执行型维护 worker。
- 服务器 Linux/Docker 环境通常不会遇到 Windows fork 问题。

### 统计接口数据为空

优先检查：

- 实验是否已有轨迹点或决策明细。
- 聚合任务是否执行成功。
- 维护任务是否已经清理原始运行数据。
- 对应时间范围是否有数据。
- compact 轨迹查询是否有 `trajectory_points_sampled_1s`。

### 热力图无法生成

优先检查：

- `heatmap_cache` 是否已有对应缓存。
- Redis 热缓存是否命中。
- 原始 `trajectory_points` 是否仍存在。
- 实验是否已经执行过 runtime data cleanup。
- 维护任务中的 heatmap prewarm 是否成功。

### 维护任务不执行

优先检查：

- `experiment_maintenance_jobs` 是否有 pending 任务。
- `scheduled_at` 是否已经到期。
- 同一实验前序任务是否 failed/running。
- RQ 是否启用并连接 Redis。
- worker 是否正在消费正确的 queue。
- 数据库行锁是否被其他 worker 持有。

## 14. 关键启动方式

从项目根目录启动后端：

```powershell
python -m backend
```

从项目根目录启动 RQ worker：

```powershell
python -m backend run-maintenance-worker
```

Windows 本地如果遇到 scheduler/fork 问题，可以关闭 scheduler：

```powershell
python -m backend run-maintenance-worker --without-scheduler
```

实际可用命令仍以 `backend/__main__.py` 当前暴露的 CLI 为准。
