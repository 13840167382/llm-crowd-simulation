# 人群流动模拟系统后端部署与运维指南

## 1. 适用范围

这份文档用于收口当前后端的部署、发布、迁移、回滚和日常排障方式，默认面向：

- API 服务进程
- PostgreSQL / TimescaleDB
- Redis
- 基于 RQ 的 maintenance worker

当前仓库还没有内置 Docker Compose、Kubernetes 或 systemd 文件，因此本文档以“手工部署步骤 + 可直接复用的示例配置”为主。Docker Compose 示例见第 9 节。

## 2. 运行拓扑

完整形态下，后端至少包含两个常驻进程：

1. API 进程
2. maintenance worker 进程

依赖关系如下：

```text
Unity / Swagger / 其他调用方
            |
            v
     FastAPI API 进程
        |        |
        |        +----> Redis
        |
        +-------------> PostgreSQL / TimescaleDB

maintenance worker
        |        |
        |        +----> Redis / RQ
        |
        +-------------> PostgreSQL / TimescaleDB
```

说明：

- API 进程负责业务接口、缓存、幂等、维护任务入队。
- maintenance worker 负责消费 experiment maintenance jobs，对应链路为：
  `analytics_refresh -> heatmap_prewarm -> runtime_data_cleanup -> experiment_archive`。
- Redis 默认开启。`X-Request-Id` 通用幂等、缓存和 RQ 链路依赖 Redis。
- 如果本地把 `APP_REDIS_ENABLED=false`，API 仍可启动，但缓存、RQ 派发和部分 Redis 相关能力会降级或关闭。
- 决策 `batch_id` 与轨迹 `batch_id` 的最终幂等事实来源是数据库唯一约束和批次表记录；Redis 锁只用于减少并发处理中重复执行。
- 生产环境应始终启用 Redis，并保证 API 与 worker 使用同一套数据库和 Redis 配置。

## 3. 前置要求

部署前请先准备：

- Python `3.12+`
- 可访问的 PostgreSQL 实例
- 已安装 TimescaleDB 扩展的数据库环境
- 可访问的 Redis 实例

当前代码默认假设：

- 数据库健康检查走 PostgreSQL，并会额外回传 TimescaleDB 就绪状态。
- maintenance worker 启动前会同时检查数据库和 Redis；任一不可用都会直接启动失败。

## 4. 环境变量加载规则

运行时会先加载 `backend/.env`，再按 `APP_ENV` 加载 `backend/.env.{APP_ENV}`。

加载规则有两个关键点：

1. 先读 `.env`
2. 再读 `.env.local` 或 `.env.production`

同时，已经存在的系统环境变量不会被 `.env` 文件覆盖。所以：

- 本地开发适合维护 `.env.local`
- 生产环境由部署系统、CI/CD 或服务管理器直接注入环境变量

示例文件：

- [`.env.example`](<.env.example>)
- [`.env.local.example`](<.env.local.example>)
- [`.env.production.example`](<.env.production.example>)

## 5. 关键环境变量说明

### 5.1 基础服务配置

- `APP_NAME`
  服务名称，主要用于 Swagger 标题和日志展示。
- `APP_ENV`
  环境名，当前主要使用 `local` / `production`。
- `APP_HOST`
  API 监听地址。
- `APP_PORT`
  API 监听端口。
- `APP_RELOAD`
  是否开启热更新。生产环境必须保持 `false`。

### 5.2 日志配置

- `APP_LOG_LEVEL`
  日志级别，常用 `debug` / `info`。
- `APP_LOG_TO_FILE`
  是否写入本地文件日志。
- `APP_LOG_DIR`
  日志目录。相对路径会解析到 `backend/` 目录下。
- `APP_LOG_FILENAME`
  原始日志文件名模板，实际落盘时会自动带当天日期。
- `APP_LOG_MAX_BYTES`
  单个日志文件大小上限。
- `APP_LOG_BACKUP_COUNT`
  日志滚动备份份数。

### 5.3 数据库配置

- `APP_DATABASE_URL`
  应用运行时使用的数据库连接串。
- `APP_ALEMBIC_DATABASE_URL`
  Alembic 迁移使用的数据库连接串。
- `APP_DB_ECHO`
  是否打印 SQLAlchemy SQL 调试输出。

### 5.4 Redis 与缓存配置

- `APP_REDIS_ENABLED`
  是否启用 Redis，默认开启。
- `APP_REDIS_URL`
  Redis 连接串。
- `APP_REDIS_KEY_PREFIX`
  统一 Redis key 前缀。
- `APP_REDIS_SOCKET_TIMEOUT_SECONDS`
  Redis socket 超时。
- `APP_HEATMAP_CACHE_TTL_SECONDS`
  热力图缓存 TTL。
- `APP_HEATMAP_PREWARM_ENABLED`
  是否在维护链路中启用热力图预热。
- `APP_HEATMAP_PREWARM_CELL_SIZE`
  预热时默认使用的热力图网格大小。
- `APP_HEATMAP_PREWARM_MAX_CROWD_TYPES`
  单次预热最多覆盖多少种 crowd type。
- `APP_SPAWN_POSITIONS_CACHE_TTL_SECONDS`
  `spawn-positions` seed 辅助缓存 TTL。

### 5.5 分析查询配置

- `APP_TRAJECTORY_QUERY_SAMPLE_INTERVAL_MS`
  秒级采样轨迹的默认采样间隔。
- `APP_TRAJECTORY_QUERY_MAX_RAW_WINDOW_MS`
  原始轨迹明细允许查询的最大时间窗口。
- `APP_TRAJECTORY_QUERY_MAX_RAW_PAGE_SIZE`
  原始轨迹明细允许的最大分页大小。

### 5.6 决策链路配置

- `APP_DECISION_ENGINE_MODE`
  当前默认是 `openai_compatible`。离线调试或纯后端压测时，可临时改为 `heuristic`。
- `APP_DECISION_PROVIDER_BASE_URL`
  外部模型服务基地址。
- `APP_DECISION_PROVIDER_API_KEY`
  外部模型服务密钥。
- `APP_DECISION_PROVIDER_MODEL`
  模型名。
- `APP_DECISION_PROVIDER_TEMPERATURE`
  采样温度。
- `APP_DECISION_PROMPT_VERSION`
  Prompt 版本号。
- `APP_DECISION_BATCH_HARD_TIMEOUT_SECONDS`
  单批决策硬超时。
- `APP_DECISION_BATCH_MAX_CONCURRENCY`
  单批决策最大并发度。
- `APP_DECISION_BATCH_LOCK_TTL_SECONDS`
  决策批次锁 TTL。
- `APP_DECISION_EXPERIMENT_LOCK_TTL_SECONDS`
  实验级锁 TTL。

### 5.7 幂等与维护任务配置

- `APP_REQUEST_IDEMPOTENCY_TTL_SECONDS`
  幂等响应快照 TTL。
- `APP_REQUEST_IDEMPOTENCY_LOCK_TTL_SECONDS`
  幂等锁 TTL。
- `APP_MAINTENANCE_QUEUE_NAME`
  RQ 队列名。
- `APP_MAINTENANCE_RQ_JOB_TIMEOUT_SECONDS`
  RQ job 超时。
- `APP_MAINTENANCE_RQ_TTL_SECONDS`
  RQ 队列中 job 的存活时间。
- `APP_MAINTENANCE_RQ_RESULT_TTL_SECONDS`
  成功结果保留时间。
- `APP_MAINTENANCE_RQ_FAILURE_TTL_SECONDS`
  失败结果保留时间。
- `APP_MAINTENANCE_WORKER_POLL_INTERVAL_SECONDS`
  本地轮询 worker 的空闲轮询间隔。
- `APP_MAINTENANCE_WORKER_IDLE_LOG_EVERY_POLLS`
  空闲心跳日志频率。
- `APP_MAINTENANCE_JOB_MAX_RETRY_ATTEMPTS`
  维护任务最大重试次数。
- `APP_MAINTENANCE_JOB_RETRY_BACKOFF_SECONDS`
  维护任务重试退避秒数。
- `APP_EXPERIMENT_RUNTIME_CLEANUP_AUTO_ENQUEUE`
  完成实验后是否自动入队 runtime cleanup。

### 5.8 本地与生产常用值

本地联调：

- `APP_ENV=local`
- `APP_HOST=127.0.0.1`
- `APP_RELOAD=true`
- `APP_LOG_LEVEL=debug`
- `APP_REDIS_ENABLED=true`；只有在轻量离线开发且不验证缓存、RQ、`X-Request-Id` 幂等时才临时改成 `false`

生产部署：

- `APP_ENV=production`
- `APP_HOST=0.0.0.0`
- `APP_RELOAD=false`
- `APP_LOG_LEVEL=info`
- `APP_REDIS_ENABLED=true`
- `APP_DB_ECHO=false`

## 6. 本地部署步骤

下面步骤默认在 [backend](/E:/26-4-11/crowdFlowSimulation/backend) 目录执行。

### 6.1 安装依赖

```bash
python -m pip install -e ".[dev]"
```

### 6.2 准备本地环境变量

```powershell
Copy-Item .env.local.example .env.local
```

`.env.local.example` 默认启用 Redis：

```text
APP_REDIS_ENABLED=true
```

如果只是轻量离线开发，且不验证缓存、RQ、`X-Request-Id` 幂等，可以临时改成：

```text
APP_REDIS_ENABLED=false
```

完整联调与生产形态验收应保持 Redis 开启，并确保本机 Redis 可连通。

### 6.3 执行数据库迁移

```bash
python -m alembic -c alembic.ini upgrade head
```

这一步会自动包含内置 crowd type 的 seed 迁移。

### 6.4 启动 API

从项目根目录 [crowdFlowSimulation](/E:/26-4-11/crowdFlowSimulation) 执行：

```bash
python -m backend
```

`backend/` 本身就是 Python 包目录，所以 `python -m backend` 默认应从它的父目录执行。这样 Python 才能找到 `backend.__main__`。

如果当前已经进入 `backend/` 目录，不需要退出目录，但必须先把父目录加入 `PYTHONPATH`：

```powershell
$env:PYTHONPATH = ".."
python -m backend
```

不设置 `PYTHONPATH` 时，在 `backend/` 目录内执行 `python -m backend` 会让 Python 查找 `backend/backend/__main__.py`，实际目录里没有这一层，因此会报 `No module named backend`。

### 6.5 启动 maintenance worker

如果希望完整验证维护链路，请保持 Redis 开启，再从项目根目录执行：

```bash
python -m backend run-maintenance-worker
```

如果当前已经进入 `backend/` 目录：

```powershell
$env:PYTHONPATH = ".."
python -m backend run-maintenance-worker
```

只想做一次性 smoke check：

```bash
python -m backend run-maintenance-worker --burst --max-jobs 5
```

在 `backend/` 目录内：

```powershell
$env:PYTHONPATH = ".."
python -m backend run-maintenance-worker --burst --max-jobs 5
```

Windows 本地联调注意事项：

- RQ `2.7.0` 的 scheduler 导入路径会使用 Unix `fork`，Windows 下可能报 `ValueError: cannot find context for 'fork'`
- 如果出现这个错误，先使用 `--without-scheduler` 规避：

```bash
python -m backend run-maintenance-worker --without-scheduler
```

如果当前在 `backend/` 目录内：

```powershell
$env:PYTHONPATH = ".."
python -m backend run-maintenance-worker --without-scheduler
```

- 关闭 scheduler 后，worker 仍会消费已经入队的普通 job
- 关闭 scheduler 后，RQ 延迟 job 不会自动唤醒；维护任务失败重试或未来时间任务到期后，需要手动执行一次补派发：

```bash
python -m backend dispatch-maintenance-jobs --limit 20 --fanout 1
```

### 6.6 本地联调后的快速验收

至少检查：

```text
GET /
GET /healthz
GET /healthz/db
GET /healthz/redis
GET /api/v1/docs
```

判断标准：

- `/healthz` 返回 `status=ok`
- `/healthz/db` 返回 `status=ok`
- `/healthz/redis`
  - 本地禁用 Redis 时允许 `status=disabled`
  - 完整链路联调时应为 `status=ok`

## 7. 生产部署步骤

### 7.1 发布前检查

发布前先确认：

1. 已备份数据库或至少具备可用快照
2. PostgreSQL / TimescaleDB / Redis 可连通
3. `.env.production` 或外部注入环境变量已准备完成
4. 维护窗口内不会有未评估的破坏性迁移风险

### 7.2 准备生产环境变量

可以直接参考 [`.env.production.example`](<.env.production.example>)。

如果采用文件方式，在 `backend/` 下放置：

```text
.env.production
```

如果采用外部注入，记得至少显式设置：

- `APP_ENV=production`
- `APP_DATABASE_URL`
- `APP_ALEMBIC_DATABASE_URL`
- `APP_REDIS_ENABLED=true`
- `APP_REDIS_URL`

### 7.3 安装依赖

在部署目标机的项目目录执行：

```bash
python -m pip install -e "./backend"
```

如果部署机直接进入 `backend/` 目录，也可以执行：

```bash
python -m pip install -e "."
```

### 7.4 执行迁移

```bash
cd backend
python -m alembic -c alembic.ini upgrade head
```

### 7.5 启动 API 进程

回到项目根目录执行：

```bash
python -m backend
```

### 7.6 启动 maintenance worker 进程

同样在项目根目录执行：

```bash
python -m backend run-maintenance-worker
```

生产环境优先使用 Linux 并保留默认 scheduler，以保证延迟重试和未来时间任务能自动唤醒。如果生产部署在 Windows，遇到 `cannot find context for 'fork'` 时可以临时使用：

```bash
python -m backend run-maintenance-worker --without-scheduler
```

使用该模式时，需要额外安排周期性补派发，例如每隔一段时间执行：

```bash
python -m backend dispatch-maintenance-jobs --limit 20 --fanout 1
```

### 7.7 发布后验收

发布完成后按顺序做下面这些检查：

1. `GET /healthz`
2. `GET /healthz/db`
3. `GET /healthz/redis`
4. `python -m backend run-maintenance-worker --burst --max-jobs 1`
5. 抽查 `GET /api/v1/crowd-types`
6. 如有待处理实验，执行一次 `show-maintenance-jobs`

## 8. Linux systemd 示例

如果生产环境使用 Linux，可以把 API 和 worker 分别托管给 systemd。下面是可直接参考的示例，路径请按实际部署目录替换。

### 8.1 API 服务示例

```ini
[Unit]
Description=Crowd Flow Backend API
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/crowd-flow/crowdFlowSimulation
Environment=APP_ENV=production
ExecStart=/opt/crowd-flow/.venv/bin/python -m backend
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

### 8.2 worker 服务示例

```ini
[Unit]
Description=Crowd Flow Backend Maintenance Worker
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/crowd-flow/crowdFlowSimulation
Environment=APP_ENV=production
ExecStart=/opt/crowd-flow/.venv/bin/python -m backend run-maintenance-worker
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

如果使用外部配置中心或 secret manager，可以把 `Environment=` 替换成更适合当前基础设施的注入方式。

## 9. Docker Compose 示例

当前仓库没有内置 Docker 文件。下面是一套可直接落地的 Compose 结构：一个镜像同时服务 API 和 worker，Compose 中拆成 `api`、`worker`、`migrate` 三个进程，并配套 TimescaleDB 与 Redis。

目录结构：

```text
crowdFlowSimulation/
  docker-compose.yml
  backend/
    Dockerfile
    .dockerignore
    .env.docker
```

### 9.1 `backend/Dockerfile`

```dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
ENV PYTHONPATH=/app

WORKDIR /app

COPY backend /app/backend

RUN python -m pip install --upgrade pip \
    && python -m pip install --no-cache-dir -e /app/backend

EXPOSE 8000

CMD ["python", "-m", "backend"]
```

这里显式设置 `PYTHONPATH=/app`，所以容器里可以直接执行 `python -m backend` 和 `python -m backend run-maintenance-worker`，不需要再手工切目录或设置 `$env:PYTHONPATH = ".."`。

### 9.2 `backend/.dockerignore`

```text
.git
__pycache__/
*.pyc
logs/
tmp/
pytest-cache-files-*/
.env.local
.env.production
```

### 9.3 `backend/.env.docker`

```env
APP_NAME=人群流动模拟系统后端
APP_ENV=production
APP_HOST=0.0.0.0
APP_PORT=8000
APP_RELOAD=false
APP_LOG_LEVEL=info
APP_LOG_TO_FILE=true
APP_LOG_DIR=logs
APP_LOG_FILENAME=backend.production.log

APP_DATABASE_URL=postgresql+psycopg://app_user:app_password@db:5432/crowd_flow_simulation
APP_ALEMBIC_DATABASE_URL=postgresql+psycopg://app_user:app_password@db:5432/crowd_flow_simulation

APP_REDIS_ENABLED=true
APP_REDIS_URL=redis://redis:6379/0
APP_REDIS_KEY_PREFIX=crowd_flow_simulation

APP_DECISION_ENGINE_MODE=heuristic
APP_MAINTENANCE_QUEUE_NAME=maintenance
```

真实模型部署时，把决策相关环境变量改成生产模型服务：

```env
APP_DECISION_ENGINE_MODE=openai_compatible
APP_DECISION_PROVIDER_BASE_URL=https://api.openai.com/v1
APP_DECISION_PROVIDER_API_KEY=替换为真实密钥
APP_DECISION_PROVIDER_MODEL=替换为真实模型名
APP_DECISION_PROVIDER_TEMPERATURE=0
```

### 9.4 `docker-compose.yml`

把这个文件放在 `crowdFlowSimulation/` 目录：

```yaml
services:
  db:
    image: timescale/timescaledb:latest-pg16
    environment:
      POSTGRES_DB: crowd_flow_simulation
      POSTGRES_USER: app_user
      POSTGRES_PASSWORD: app_password
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app_user -d crowd_flow_simulation"]
      interval: 5s
      timeout: 5s
      retries: 20

  redis:
    image: redis:7
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 5s
      retries: 20

  migrate:
    build:
      context: .
      dockerfile: backend/Dockerfile
    env_file:
      - backend/.env.docker
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    command: sh -c "cd /app/backend && python -m alembic -c alembic.ini upgrade head"
    restart: "no"

  api:
    build:
      context: .
      dockerfile: backend/Dockerfile
    env_file:
      - backend/.env.docker
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    command: python -m backend
    ports:
      - "8000:8000"

  worker:
    build:
      context: .
      dockerfile: backend/Dockerfile
    env_file:
      - backend/.env.docker
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    command: python -m backend run-maintenance-worker

volumes:
  pgdata:
```

如果数据库和 Redis 已经由云服务提供，Compose 中可以删除 `db` 和 `redis` 服务，并把 `.env.docker` 里的 `APP_DATABASE_URL`、`APP_ALEMBIC_DATABASE_URL`、`APP_REDIS_URL` 改成云服务地址。

### 9.5 Docker 启动顺序

```bash
cd /opt/crowd-flow/crowdFlowSimulation

docker compose build
docker compose up -d db redis
docker compose run --rm migrate
docker compose up -d api worker
```

查看日志：

```bash

```

健康检查：

```bash

```

```bash

docker compose up -d api worker
```

## 10. 健康检查与验活

### 10.1 HTTP 健康接口

- `GET /`
  查看服务名、版本、环境和 docs URL。
- `GET /healthz`
  基础进程健康检查。
- `GET /healthz/db`
  数据库健康检查，同时会回传 TimescaleDB 状态。
- `GET /healthz/redis`
  Redis 健康检查；禁用 Redis 时会返回 `disabled` 而不是 503。

### 10.2 数据库健康检查的关注点

`/healthz/db` 正常时应至少关注：

- `status=ok`
- `connected=true`
- `timescaledb.available`
- `timescaledb.installed`
- `timescaledb.ready`
- `timescaledb.trajectory_points_hypertable`
- `timescaledb.trajectory_points_compression_enabled`
- `timescaledb.trajectory_points_chunk_interval_ms`

如果这里失败，worker 也会因为启动预检查失败而无法启动。

### 10.3 Redis 健康检查的关注点

生产环境要求：

- `status=ok`

本地开发允许：

- `status=disabled`

但一旦 Redis 是 `disabled`，下面这些链路就不应该按“完整生产形态”来验收：

- RQ maintenance worker
- request idempotency 快照
- heatmap 热点缓存
- spawn seed 辅助缓存

## 11. 维护任务运维命令

所有命令默认在项目根目录 [crowdFlowSimulation](/E:/26-4-11/crowdFlowSimulation) 执行。

### 11.1 查询维护任务

```bash
python -m backend show-maintenance-jobs --experiment-id exp_xxx
```

只看失败任务：

```bash
python -m backend show-maintenance-jobs --experiment-id exp_xxx --status failed
```

附带结果详情：

```bash
python -m backend show-maintenance-jobs --experiment-id exp_xxx --include-result
```

### 11.2 手动补派发到 RQ

```bash
python -m backend dispatch-maintenance-jobs --limit 20 --fanout 1
```

适用场景：

- worker 中断后补派发
- 想验证数据库 truth source 与 RQ 同步是否正常
- Windows 下 worker 使用 `--without-scheduler` 时，手动唤醒已到期的失败重试或未来时间维护任务

### 11.3 直接执行一轮待处理任务

```bash
python -m backend run-maintenance-jobs --limit 20
```

这个入口适合：

- 单机调试
- 不想经过 RQ 时的临时排障

### 11.4 重置失败任务

```bash
python -m backend reset-maintenance-jobs --experiment-id exp_xxx
```

只重置某一条失败任务：

```bash
python -m backend reset-maintenance-jobs --experiment-id exp_xxx --job-id 123
```

如果只想改数据库状态，不立即补派发：

```bash
python -m backend reset-maintenance-jobs --experiment-id exp_xxx --without-dispatch
```

### 11.5 从指定任务开始重放后面的链路

```bash
python -m backend replay-maintenance-jobs --experiment-id exp_xxx --from-job-id 123
```

如果只重置状态，不补派发：

```bash
python -m backend replay-maintenance-jobs --experiment-id exp_xxx --from-job-id 123 --without-dispatch
```

### 11.6 清理实验运行期原始数据

```bash
python -m backend cleanup-runtime-data --experiment-id exp_xxx
```

保留热力图缓存：

```bash
python -m backend cleanup-runtime-data --experiment-id exp_xxx --keep-heatmap-cache
```

## 12. 发布、迁移与回滚

### 12.1 标准发布顺序

按下面顺序发布：

1. 停止写入或进入维护窗口
2. 备份数据库
3. 更新代码与依赖
4. 执行 `alembic upgrade head`
5. 启动或重启 API
6. 启动或重启 maintenance worker
7. 执行健康检查与 worker smoke check

### 12.2 常用迁移命令

查看当前 revision：

```bash
python -m alembic -c alembic.ini current
```

升级到最新：

```bash
python -m alembic -c alembic.ini upgrade head
```

回滚一个版本：

```bash
python -m alembic -c alembic.ini downgrade -1
```

回滚到指定 revision：

```bash
python -m alembic -c alembic.ini downgrade <revision>
```

### 12.3 回滚原则

数据库回滚前先确认：

1. 新版本是否已经写入新结构数据
2. 是否存在不可逆的数据清理或聚合结果
3. 当前 revision 与目标 revision 是否经过演练

不要在“应用继续对外写入”的情况下直接执行 downgrade。

更稳妥的回滚顺序通常是：

1. 先停 API 和 worker
2. 回退代码版本
3. 评估是否需要执行 Alembic downgrade
4. 如需 downgrade，先做数据库快照后再执行
5. 重启 API 和 worker
6. 再次执行健康检查

## 13. 日志与排障

### 13.1 日志落盘规则

当前日志同时支持控制台输出和本地文件输出。

关键行为：

- 相对 `APP_LOG_DIR` 会被解析到 `backend/` 目录下
- `APP_LOG_FILENAME` 会自动加上当天日期
- 文件日志按 `APP_LOG_MAX_BYTES` 滚动
- 最多保留 `APP_LOG_BACKUP_COUNT` 份

例如：

- `APP_LOG_DIR=logs`
- `APP_LOG_FILENAME=backend.production.log`

实际文件名会像：

```text
backend/logs/backend.production-2026-04-15.log
```

### 13.2 Windows 日志轮转说明

Windows 下如果日志文件被其他进程占用，当前实现会临时跳过本次滚动并继续写入原文件，同时向 `stderr` 打出提示。

这意味着：

- 看到一次“日志轮转遇到文件占用”不代表服务不可用
- 如果频繁出现，优先检查日志采集器、编辑器或杀毒软件是否长期占用日志文件

### 13.3 常见排障路径

#### 场景一：API 能启动，但 `/healthz/db` 返回 503

排查顺序：

1. 检查 `APP_DATABASE_URL`
2. 检查数据库账号、密码、主机和端口
3. 检查数据库实例是否可达
4. 检查 TimescaleDB 扩展是否已安装并可用
5. 执行 `python -m alembic -c alembic.ini current`

#### 场景二：`/healthz/redis` 返回错误或 worker 无法启动

排查顺序：

1. 检查 `APP_REDIS_ENABLED` 是否误设为 `false`
2. 检查 `APP_REDIS_URL`
3. 确认 Redis 网络可达
4. 再启动一次：

```bash
python -m backend run-maintenance-worker --burst --max-jobs 1
```

如果 worker 启动即退出，并打印 `code=4002` 对应的 JSON，一般就是数据库或 Redis 预检查未通过。

Windows 下如果看到 `ValueError: cannot find context for 'fork'`，这是 RQ scheduler 的 Windows 兼容问题。先用下面的命令验证普通队列消费：

```bash
python -m backend run-maintenance-worker --burst --max-jobs 1 --without-scheduler
```

#### 场景三：实验完成后没有看到维护任务被消费

排查顺序：

1. 查询任务状态：

```bash
python -m backend show-maintenance-jobs --experiment-id exp_xxx --include-result
```

2. 如果任务停留在 `pending`，手动补派发：

```bash
python -m backend dispatch-maintenance-jobs --limit 20 --fanout 1
```

3. 用 burst worker 再验证一次：

```bash
python -m backend run-maintenance-worker --burst --max-jobs 5
```

4. 若仍失败，再看日志中的 `failed` 任务详情或执行 `reset-maintenance-jobs`

#### 场景四：日志文件没有生成

排查顺序：

1. 检查 `APP_LOG_TO_FILE=true`
2. 检查 `APP_LOG_DIR` 对应目录是否可写
3. 确认服务实际工作目录与预期一致
4. 检查是否只看了未带日期后缀的原始文件名

#### 场景五：本地运行 `python -m pytest` 收集到 `pytest-cache-files-*`

本地多次测试后，目录下可能留下 `pytest-cache-files-*` 临时目录。不要让 pytest 扫描整个 `backend/` 目录，直接指定测试目录：

```bash
python -m pytest tests -q -p no:cacheprovider
```

也可以按范围拆开执行：

```bash
python -m pytest tests/unit -q -p no:cacheprovider
python -m pytest tests/integration -q -p no:cacheprovider
python -m pytest tests/e2e -q -p no:cacheprovider
```

## 14. 发布后检查清单

每次发布后，至少完成下面这些检查：

1. API 进程和 worker 进程都在运行
2. `/healthz` 返回 `ok`
3. `/healthz/db` 返回 `ok`
4. `/healthz/redis` 在生产环境返回 `ok`
5. `GET /api/v1/crowd-types` 可正常返回数据
6. `python -m backend run-maintenance-worker --burst --max-jobs 1` 可正常执行
